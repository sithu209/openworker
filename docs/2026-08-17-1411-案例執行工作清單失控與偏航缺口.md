# OpenWorker：案例執行工作清單失控與偏航缺口

> **2026-08-20 CURRENT CONTRACT OVERRIDE — HISTORICAL DESIGN**
>
> 本文件記錄 2026-08-17 為解決案例偏航而形成 CaseWorklist 的歷史設計。**CaseWorklist、dependency、repair-parent、acceptance gate 等治理思想仍有效；但 OpenWorker 不再是目前 controller，GitHub Actions scheduler 也不是現行 business authority。**
>
> 現行架構：go-tool 負責告訴大模型可用 capability / inputs / guidance / negative knowledge；DirectWork 是唯一 business controller / durable work authority；必要時 GitHub Action 只送短密語；不同、依賴已滿足且可安全並行的 durable works 可由多 slot/executor 併發。現行 `case-worklists/0002.json`～`0005.json` 已升級為 `directwork-case-worklist/v2`。

時間：2026-08-17 14:11（Asia/Taipei）

狀態：HISTORICAL GAP / GOVERNANCE PRINCIPLES RETAINED

## 1. 問題

OpenWorker 目前在做 Case 0002 / 0003 / 0004 這類跨 repo REAL 案例時，已經有：

- AI-Engineering-OS Project / Job；
- JobBinding；
- ProjectKnowledge；
- WorkLedger / artifact / review / delivery；
- go-tool-runtime capability discovery；
- 詳實案例 Markdown 手冊。

但仍缺少一個 **case-level canonical worklist / execution state machine**。

結果是：

```text
案例目標
→ 操作者/LLM記得一部分下一步
→ 遇到 blocker
→ 臨時追一條旁支
→ 又發現另一個 infrastructure gap
→ 再改另一層架構
→ 原案例主線被擱置
```

所以系統「記錄很多」，但沒有一個機器可驗證的 authority 告訴 OpenWorker：

1. 全案例工作清單是什麼；
2. 現在完成到哪一步；
3. 唯一允許執行的下一步是什麼；
4. 哪些工作只是 blocker repair，完成後必須回到哪個原始 step；
5. 哪些新工作根本不屬於本案例，禁止插入。

這就是案例執行偏航的根因。

> **2026-08-20 更正**：上段的根因分析仍成立，但「authority 告訴 OpenWorker」改為「DirectWork durable work + current case worklist contract 告訴執行器」。

## 2. 根因

現有模組責任切得很清楚，但缺少 orchestration control plane：

- `project_lifecycle.py`：Project bootstrap；
- `engineering_os.py`：OS API；
- `digital_thread.py`：provenance；
- review / delivery：成果治理；
- go-tool-runtime：工具 discovery；
- case docs：人工 audit trail。

這些都不是「案例工作清單 authority」。

目前真正的執行順序仍靠 LLM / operator 在上下文中維持，因此長案例一定容易漂移。

## 3. 正式修復方向：CaseWorklist

OpenWorker 必須新增一個 durable、typed、fail-closed 的 `CaseWorklist`。

每個案例在開始 REAL work 之前，先建立完整主鏈：

```text
Case
  steps[]
    step_id
    title
    kind
    dependencies[]
    allowed_actions[]
    acceptance[]
    status
    evidence[]
    blocker
    repair_parent_step
```

正式狀態只允許：

```text
PENDING
READY
RUNNING
BLOCKED
PASSED
FAILED
SKIPPED（只有 manifest 明確允許時）
```

> **2026-08-20 更正**：結構思想保留，但實際 authority 已遷移到 `directwork-case-worklist/v2`；step execution 必須對應 DirectWork `work_id` 與 durable events/evidence。

## 4. 最重要的控制規則

### 4.1 一次只能有一個 canonical next step

OpenWorker 每次動作前必須：

```text
worklist.next_step()
→ assert_action_allowed(step_id, action_id)
→ dispatch
```

不能先 dispatch 再補文件。

> **2026-08-20 更正**：這條「一次只能一個」對新版並行架構過於嚴格。現行語意是：dependency graph 決定 READY set；不同且可安全並行的 READY durable works 可以同時 dispatch。只有同一不可重入 work 保持 single active claim/lease。

### 4.2 不允許跳步

若 dependencies 未 PASS：

```text
assert_action_allowed() → fail closed
```

此原則仍有效；現行由 DirectWork + case worklist contract 驗證。

### 4.3 blocker repair 必須綁回原 step

例如 Case 0004 的 source locator 缺 O87 label：

```text
C-010 locate source
  ↓ BLOCKED
R-C010-001 bootstrap O87 label
  ↓ PASSED
return_to = C-010
```

修 infrastructure 只是 repair child，不得把 repair branch 變成新主線。

此治理思想仍有效。

### 4.4 新工作必須先登記

LLM 發現一個新缺口時，不得直接開始修。

必須先：

```text
worklist.add_repair(parent_step, ...)
```

若不能指出 parent_step，表示它不是目前案例必要工作，禁止執行。

現行實作應由 DirectWork/worklist contract 建立可追溯 durable repair work，而不是依賴聊天上下文。

### 4.5 evidence gate

一個 step 只有在 acceptance evidence 完整時才能 `PASSED`。

GitHub run `success`、artifact upload 成功、queue succeeded 都不能自動等於 step PASS。

此原則完全保留；現行至少要結合 `work_id`、events、slot/executor、exit code、artifact path/size/SHA256，Drive review 時還需要 remote verification 與 exact Drive revision identity。

## 6. 持久化

第一版採 workspace authority：

```text
<workspace>/.openworker/case-worklist.json
```

原因：

- 與 JobBinding 同屬 job-scoped state；
- 不依賴聊天上下文；
- runner 重啟後可續；
- 可放進案例 evidence；
- 後續可同步進 WorkLedger / ProjectKnowledge，但不讓多份資料互相爭 authority。

> **2026-08-20 更正**：`.openworker/` 路徑與 OpenWorker authority 只保留為歷史狀態資料。新 durable execution/state authority 應歸 DirectWork；舊 workspace state 可作 migration/provenance evidence。

## 7. 驗收

P0 必須證明：

1. 可建立 deterministic worklist；
2. duplicate step id fail closed；
3. dependency cycle fail closed；
4. READY set 可被 deterministic 計算；
5. 未完成 dependency 不可 dispatch；
6. action 不在 allowlist 不可 dispatch；
7. repair step 必須有 parent；
8. repair PASS 後回到 parent step；
9. 未有 acceptance evidence 不可標 PASSED；
10. JSON round-trip 後狀態一致；
11. 對可並行 READY works，DirectWork 能建立多個 durable work 並提供真實 slot/executor 證據。

## 8. 架構邊界

歷史 `CaseWorklist` 不取代：

- AI-Engineering-OS Job lifecycle；
- WorkLedger；
- go-tool-runtime；
- case manual；
- GitHub Actions scheduler。

> **2026-08-20 CURRENT**：GitHub Actions scheduler 不再屬於 business control plane；go-tool 是 query/guidance layer；DirectWork 才是 current orchestration / durable execution authority。

目前它的現行責任應理解為：

**Case worklist 描述依賴、允許能力、acceptance 與 repair 關係；DirectWork 依這個 contract 建立與執行 durable works，讓每一步都能回答「這是不是目前允許執行的 READY work，以及證據是否足夠」。**
