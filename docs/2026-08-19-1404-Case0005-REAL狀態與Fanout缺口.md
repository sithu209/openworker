## 2. Authority 分工

統一規則：

> **流程問 OpenWorker；工具問 go-tool。**

- **OpenWorker Go**：Case 流程 authority，負責 Case status、current work、依賴、READY step、reconcile、continue、fanout、join、blocker 與下一步是否合法。
- **go-tool-runtime `:8848`**：工具/執行 authority，負責 capability contract、durable local-work queue、claim、executor、工具執行、4-slot health 與 execution evidence。
- 大模型不得依聊天記錄自行猜下一步，也不得繞過 OpenWorker 手工建立 business work。

## 3. 正確控制鏈

```text
ChatGPT / LLM
  -> command-requests/oda.json
  -> short-lived GitHub Action
  -> ODA openworker.exe / openworkerctl.exe
  -> OpenWorker Go Case Engine / Local Supervisor
  -> go-tool-runtime :8848 durable local-work queue
  -> 4 local claim slots
  -> 4 local executor slots
  -> owning tool capability
  -> durable result / ledger
  -> OpenWorker reconcile / fanout join
  -> command-results/oda/<request_id>/final.json
  -> ChatGPT read-back
```

GitHub Action 只負責把高階短命令送到指定電腦並取得 acceptance/receipt；不得等待長業務完成、不得承擔 business execution、不得作 artifact authority。

### 3.1 GitHub Action 與本機 Action 嚴格區分

- **GitHub Action**：`ChatGPT -> 指定電腦本機總控` 的一次性短命令 transport。
- **本機 Action**：OpenWorker / go-tool 在目標電腦內部調度的 claim slot、executor slot 與 owning-tool capability 執行鏈。

Canonical 表述固定為：

> **GitHub Action 下短命令給本機總控；本機總控再把 business work 分發給本機多個 Action/executor 並行執行。**

## 4. 本機 4-Slot 並行

1. OpenWorker 判斷 READY step；
2. 單步建立一個 durable work，fanout 建立 deterministic child works；
3. durable works POST 到 `:8848/api/execution/local-work`；
4. `gtr-work-agent` 以 `GTR_LOCAL_WORKERS=4` 維持 4 個 claim slots；
5. `gtr-work-executor` 維持 4 個 executor slots；
6. executor 以 `localexec.Registry.Execute(...)` 執行 owning capability；
7. terminal result/error 回寫 durable queue；
8. OpenWorker reconcile，fanout 時 join，再決定下一 READY step。

真正並行是：

> **OpenWorker fanout + go-tool durable queue + 4 claim slots + 4 executor slots。**

不是多個 GitHub workflow 做 business execution。

## 5. 強制 4-Slot 追蹤與回報規則

從本次修正開始，任何 `case status` / `case_work_status` 都不能只回報 Case 的 `pending / running / completed / failed`。

**每次 Case 進度查詢必須同時附帶 `local_supervisor` 4-slot snapshot。**

最低必須回報：

- `status` / `operational`；
- `fresh_claim_slot_count` 與 `required_claim_slots=4`；
- `fresh_executor_slot_count` 與 `required_executor_slots=4`；
- `claim_slots`：4 個 claim slot 的 heartbeat / runner 狀態；
- `executor_slots`：4 個 executor slot 的 heartbeat / runner 狀態；
- `active_slots` / `free_slots` / `max_parallel_actions`；
- queue：`pending` / `claimed` / `inflight` / `queued` / `completed` / `failed`；
- `recent_events`；
- `observed_at`。

go-tool 的 canonical endpoint 為：

`GET /api/execution/local-supervisor/status?machine=<COMPUTERNAME>&limit=200`

它已提供 schema `gtr-local-supervisor-status/v4` 與上述 4-slot 欄位。

OpenWorker `case status` 必須把這份結果合併為：

`local_supervisor`

若 supervisor 查詢失敗，也不得靜默忽略，必須回：

`local_supervisor_error`

### 5.1 大模型判斷規則

- Case `pending` + 4 executor slots 全 idle/free：優先判定 queue/claim 路徑異常，不得說「還在正常做」。
- Case `claimed/running` + 某 slot 長時間 busy：追該 executor / capability 的 leaf blocker。
- work `completed` + Case 未前進：追 OpenWorker reconcile blocker。
- fresh claim/executor slot 少於 4：本機總控為 `DEGRADED`，先修 slot health。
- 看不到 4-slot snapshot：**狀態回報不完整**，不得宣告 Case 正常執行。
