## 1. 核心定位

每一個 OpenWorker 工作都應像一個「小型 Git repo」。

它不是單純 queue、agent session 或工具執行器，而是一個可持久追蹤的工作帳本，必須保存：

- 工作目標與輸入；
- 當前計畫與計畫版本；
- 每一步執行；
- 每一步使用的 capability / owning repo / runner；
- 每一個真實產物與 SHA256 / size / path / provenance；
- 驗收結果與驗收依據；
- 失敗、blocked、skip、timeout；
- 缺口判定與 owning repo；
- 返工請求；
- 返工前基準；
- 返工後新 revision；
- 再次驗收；
- 最終 delivery revision；
- 完整歷史，禁止覆寫與抹除。

概念上：

```text
Work = repository
WorkRevision = commit
ArtifactSet = tree
ParentRevision = parent commit
Acceptance = protected status check
Rework = new child revision, never overwrite parent
Delivery = accepted tag / release
CurrentState = HEAD
```

OpenWorker 不需要真的用 Git object database，但資料語義必須達到相同治理效果：append-only、可比較、可追蹤 parent、可重新驗收、可回到上一個 accepted revision。

## 2. Case 0003 暴露的真正缺口

Case 0003 已有大量 REAL run/job/artifact evidence，也有 project snapshot 與歷史 failure events，但目前仍有四個治理缺口：

### G1 — Audit event 不等於工作 revision

現有 `coworker/audit.py` 主要記錄 connector/tool action。它能回答「呼叫了什麼」，但不能完整回答：

- 這次修改屬於哪一個 work revision？
- parent revision 是誰？
- revision 的目標、計畫與 artifact tree 是什麼？
- 哪一份 acceptance 把它標成可交付？
- 哪一次返工取代了哪一個 revision？

因此 audit log 要保留，但不能當成 work history 的唯一權威資料。

### G2 — Project lifecycle 只有 create/ensure，缺 revision state machine

現有 `EngineeringOSProjectClient` 能 create / ensure OS Project，但 OpenWorker 自己缺少完整的：

```text
WORK_OPEN
→ REVISION_OPEN
→ EXECUTING
→ VERIFYING
→ ACCEPTED | REWORK_REQUIRED | BLOCKED | FAILED
→ new child REVISION
→ VERIFYING
→ ACCEPTED
→ DELIVERED
```

尤其 `REWORK_REQUIRED` 必須是一級正式狀態，不能只存在自然語言 log。

### G3 — 返工不可被覆蓋

返工必須建立新的 revision：

```text
r1 REAL output
  ↓ acceptance failed
r2 rework of r1
  ↓ acceptance failed
r3 rework of r2
  ↓ accepted
```

r1/r2 必須永久保留。OpenWorker 不可把 r3 的結果直接覆蓋到 r1，也不能只保存最新 `current_status=completed`。

每個 rework revision 至少要記錄：

- `parent_revision_id`
- `rework_of_revision_id`
- `reason`
- `gap_owner_repo`
- `changed_contracts`
- `changed_artifacts`
- `verification_plan`
- `acceptance_result`

### G4 — 「完成」缺獨立 Final Acceptance Gate

Case 0003 的歷史 REAL 成功仍有效，但未來 OpenWorker 對任何工作只能在以下條件全部滿足後把 HEAD 標成 accepted/delivered：

- revision 有 parent/history；
- 所有 required steps terminal；
- required product steps 非 all-skipped；
- required artifacts 真實存在且非零；
- artifact path bounded；
- SHA/provenance 完整；
- acceptance checks 全 pass；
- 沒有 unresolved blockers；
- 沒有 open rework request；
- delivery 指向明確 accepted revision。

若任何一項不成立，只能是 `VERIFYING / REWORK_REQUIRED / BLOCKED / FAILED`，不得 `CLOSED`。

## 3. 要補的 OpenWorker 資料模型

新增 durable `WorkLedger`，最小 schema：

```text
works
  work_id
  code
  title
  workspace
  status
  head_revision_id
  accepted_revision_id
  delivered_revision_id
  created_at
  updated_at

work_revisions
  revision_id
  work_id
  revision_no
  parent_revision_id
  kind              # initial | progress | rework | acceptance | delivery
  status
  goal
  plan_json
  reason
  gap_owner_repo
  created_at

work_artifacts
  artifact_id
  revision_id
  logical_name
  path
  sha256
  size_bytes
  provenance_json
  verification_status

work_checks
  check_id
  revision_id
  name
  required
  status
  evidence_json
  reason

work_events
  event_id
  revision_id
  event_type
  payload_json
  created_at
```

所有 revision/event 採 append-only；只有 `works.head_revision_id / accepted_revision_id / delivered_revision_id` 是可移動指標。

## 4. 返工控制規則

1. `accepted` revision 不可原地修改。
2. 已存在 artifact 的 SHA 改變，必須新 revision。
3. acceptance fail 必須建立/標記 `REWORK_REQUIRED`，不能直接重新跑後覆蓋舊 evidence。
4. 新返工必須以失敗 revision 為 parent 或明確 `rework_of_revision_id`。
5. 新 revision 完成後重新做完整 required checks。
6. `accepted_revision_id` 只有 acceptance gate 可以更新。
7. `delivered_revision_id` 必須指向 accepted revision。
8. 可把 HEAD 移回歷史 accepted revision 作為「治理回退」，但不能刪除後續 revisions。
9. owning repo 的程式返工與 OpenWorker work revision 分離：OpenWorker 記錄「為什麼返工、修了哪個 repo/commit、重跑得到什麼」，不複製 owning repo 的產品邏輯。

## 5. Case 0003 最終獨立驗收如何記錄

Case 0003 現有成功鏈繼續作為 seed evidence：

```text
DTM Catalog
→ AOI
→ Consumer
→ Blender REAL
→ SceneX REAL
→ OS Artifact Registry
→ Review
→ Delivery Revision
→ website/index.html
```

補完 WorkLedger 後，應把這批歷史 evidence import 成一個 baseline revision，例如：

```text
work = CASE-0003-YUJING-BRIDGE
revision = r1
kind = acceptance-import
status = accepted
```

並建立 required checks：DTM/AOI/Consumer/Blender/SceneX/OS/Delivery。

之後任何 regression 或功能擴充都必須從 r1 建 r2/r3，不可改寫 r1。

## 7. 驗收標準

本缺口只有在以下條件成立才可關閉：

```text
一個全新工作可建立 ledger
→ 多次執行形成 revision chain
→ 失敗能被標記並產生 rework revision
→ 舊 revision/evidence 永久保留
→ required checks fail-closed
→ 新 revision pass 後 accepted pointer 更新
→ delivery 只能指 accepted revision
→ process restart 後完整 history 仍可查
```

屆時 OpenWorker 才真正具備「工作的 Git」能力：不只知道現在做完了什麼，也知道怎麼做到、哪裡失敗、返工了幾次、每次成果差在哪、最後哪一版被正式驗收與交付。
