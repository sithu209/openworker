## 1. 驗收目標

本案例不只驗證影片是否能生成，還必須驗證新版架構：

```text
GitHub Action transport
        |
        | one short dispatch
        v
ODA local OpenWorker Go node
        |
        +--> Agent slot A01 / durable job
        +--> Agent slot A02 / durable job
        +--> Agent slot A03 / durable job
        +--> Agent slot A04 / durable job
        |
        v
same CaseWorklist / same workspace / same durable authority
```

Action 只負責把工作送入 ODA；收到 durable ACK 後即可結束。長任務生命週期由 OpenWorker 管理，不能讓 GitHub Action 或 LLM context 成為 job authority。

## 5. VIDEO 階段動態 fan-out

圖像 storyboard 在 `0005-057` 批准後：

```text
0005-057
   |
   +--> shot-001 durable video job
   +--> shot-002 durable video job
   +--> shot-003 durable video job
   +--> shot-004 durable video job
   ...
   |
   +---- all terminal succeeded ----> 0005-070 finalize
```

每個 shot 都有獨立 job_id、progress、receipt、MP4、SHA256、decode/QC。不能因其中一個 shot 卡住而讓 Supervisor 無法處理其他工作。

如果 shot 數 > 本機 slot 數，OpenWorker 自己排隊；LLM 不建立第二套 scheduler。

## 6. 本機總控驗收證據

第一輪至少要取得：

1. transport Action 在 ODA 接單。
2. `COMPUTERNAME` receipt 是 `DESKTOP-ODAQN0D`。
3. transport receipt 有 4 筆 accepted durable ACK。
4. OpenWorker `/v1/cluster/agents` 顯示可用 slot。
5. 至少 2 個 job 的 running interval 重疊，證明不是假並行。
6. transport Action 可以先結束，而 durable jobs 繼續。
7. Supervisor snapshot/recover 能重新找到這些 jobs。
8. 任一 job failure 不會抹掉其他 job 狀態。
9. 一鍵 drain 只在 blockage 時使用，清完回原 canonical step。
10. Director 真實 receipt 完成後才推進 `0005-020`。

## 7. 判斷「並行有效」的方法

不能只看四個 job 都 success。真正並行 evidence 至少需要：

```text
job A started_at < job B finished_at
AND
job B started_at < job A finished_at
```

或等價的多 job running snapshot，並記錄 agent_slot。

若四個 job 依序占用同一 slot，則只證明 durable queue 有效，不能宣稱 parallel verified。

## 8. 故障閉環

若本輪出現：

- ODA Action queued 很久
- OpenWorker 8787 不通
- 只有一個 slot 可用
- gh 未登入
- owning workflow 不存在
- job accepted 但 stale
- lock 誤衝突造成串行

處理規則：

```text
OpenWorker failure receipt
→ go-tool 查 capability / negative knowledge
→ 修 owning repo
→ 更新 go-tool
→ 更新本案例手冊
→ 只重跑必要 job
```

不得用手工 shell 成果冒充 durable closure。
