# Case 0003 玉井橋：正射影像與街景黑圖語義驗收缺口

日期：2026-08-18

## 背景

Case 0003 目前已把 DTM/DEM 幾何、Blender REAL 地形與 SceneX REAL Region Pack 主線跑通，但實體成果審查又暴露兩個影像層缺口：

1. SceneX 地表仍是純色材質，沒有把原設計中的正射影像作為地表貼圖帶進 Region Pack / SceneX。
2. 街景產物可以非空、SHA256 正確、provider provenance 完整，但實體畫面仍可能是一片黑；現有 Case 0003 driver 也只驗證四方向 PNG 存在與 SHA，會錯誤復用歷史黑圖。

這兩項都不能算 Case 0003 完成。

## 缺口 A：既有正射影像能力在整合 SceneX Region Pack 時遺失

追溯 Git 歷史後已確認，這不是一個尚未設計的新能力，而是 **Case 0003 漏接既有能力**。

`liuxb99/AI-Engineering-OS` 已有三個權威實作提交：

- `b23e8406079949d23beb1b5e0e09559f51e614d8`：NLSC job-scoped 正射影像取得，輸出 `site-imagery/v1`，保存 provider、layer、EPSG:4326 bounds、image_path、SHA256、尺寸與 usage policy。
- `298d416963b24951a6ee25f4293594786cc083f2`：將 georeferenced orthophoto 套用到 Godot terrain，透過 terrain coordinate transform 把 WGS84 四角轉為 assembly CRS，取得 local X/Z bounds，再以 world/projected-plane shader 貼圖，輸出 `scenex-textured-assembly/v1`。
- `3d985ab7a702b2631d14646f2663a096ad7f1ac1`：依 site context 自動決定正射影像範圍、view mode、target GSD 與 WMS 尺寸。

因此本輪不得另造第二套互不相容的正射格式；應把 `site-imagery/v1` / `scenex-textured-assembly/v1` 的既有 provenance 與 mapping 契約接回 SceneX Region Pack。

### 已確認的整合斷點

目前 `SceneX/tools/build_region_pack_from_terrain_grid.py` 只輸出 `terrain_chunks / osm / gameplay / attribution`，沒有 imagery；`region_pack_file_loader.gd` / `region_pack_runtime.gd` 也沒有 imagery 驗證；`terrain_geometry_adapter.gd` 只接受一個外部 `material`；而 Case 0003 REAL browse 還會主動注入綠色純色 `StandardMaterial3D`。所以工作目錄即使已有正射影像，現行 Case 0003 路徑也不可能顯示它。

### 座標方向不可直接照搬

AI-Engineering-OS 舊 assembly 的貼圖轉換使用：

`local_z = -(projected_y - terrain_origin_y)`

目前 SceneX Region Pack builder 則明確採用：

`local_z increases with projected_y`

所以舊 `local_bounds_xz` 不能原樣複製。橋接時必須做 Z 方向契約轉換並把轉換方式寫入 provenance；否則可能出現南北翻轉或錯位，而不能因「有看到貼圖」就算成功。

### 正射影像最終驗收

- 正射影像為真實 NLSC/權威來源影像，不是 placeholder / 單色圖。
- 影像範圍、CRS/地理邊界與 terrain grid/AOI 可追溯。
- Region Pack 明確攜帶 texture path/SHA、provider/layer、mapping bounds 與座標方向契約。
- SceneX production terrain adapter 自己載入正射材質；不能只在測試腳本裡臨時塞材質。
- SceneX REAL 載入後地形表面可辨識真實影像紋理。
- 貼圖與地形沒有明顯翻轉、錯位、拉伸或全黑。
- BAT 正式啟動 SceneX 時也必須看到相同貼圖結果。

## 缺口 B：街景黑圖仍可通過兩層機械驗收

### B1：Terrain_To_DXF stitch 原本只驗檔案結構

`Terrain_To_DXF/internal/streetview/tiles_stitch.go` 的 `StitchMasterPanorama` 原本只驗證 tile set、SHA256、decode、尺寸、stitched PNG 與輸出 SHA。因此「所有瓦片合法但畫面近純黑」仍可形成結構上合法 evidence。

本輪已開始在 owning repo 補 fail-closed semantic visibility：

- `luma_mean`
- `luma_stddev`
- `luma_min` / `luma_max`
- `luma_range`
- `non_black_pixel_ratio`
- `visibility_samples`
- `semantic_visible`

近純黑 / 近單色 panorama 必須直接 error，不得 PASS。

### B2：Case 0003 OS driver 仍會復用歷史黑截图

`AI-Engineering-OS/scripts/case0003_openworker_os_driver.py::validate_streetview()` 現行只要求：

- manifest 存在；
- heading 正好為 0/90/180/270；
- PNG 存在非空；
- SHA256 相符。

完全沒有 semantic visibility 判斷，之後還會把這批檔案記成 `reused/completed`。因此僅修 stitch 不夠；Case driver 必須禁止復用沒有可見性 evidence 的舊黑圖，讓下一輪真正重新取得影像。

### 街景最終驗收規則

Case 0003 街景只有在以下條件同時成立時才能 PASS：

1. Google/指定 provider provenance 與 attribution 驗證通過；
2. panorama/tile 或四方向 render 來源和 SHA 完整；
3. image 非空且可解碼；
4. semantic visibility gate 通過；
5. 實體畫面可看到有意義的道路/環境內容，不是黑圖、空圖或只剩 browser chrome；
6. Case driver 不得復用不帶 semantic evidence 的舊結果；
7. ChatGPT 對實體街景圖做最終語義審查。

## Case 0003 重跑範圍

不重跑已驗證的 DTM/AOI/Blender。只重跑受影響的影像與呈現階段：

1. 街景 provider capture / tile acquisition / stitch；
2. NLSC 正射影像取得與既有 mapping contract；
3. SceneX Region Pack imagery bridge / production terrain material；
4. SceneX REAL browse；
5. fresh review revision；
6. Google Drive 實體成果審查；
7. PASS 後才進 WorkLedger / Delivery Revision；
8. 最後 `Open-Case0003-SceneX.bat` 實機打開 SceneX，確認真正貼圖地形與場景成果。
