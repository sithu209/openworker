## GitHub transient command transport —— 2026-08-19 新決策

### 問題背景

舊架構是：

`ChatGPT -> GitHub Actions -> self-hosted runner -> PowerShell/Python/工具長任務 -> 等工作完成 -> workflow 結束`

這造成三個問題：

1. self-hosted runner 被長任務佔住，後續 workflow 塞車；
2. 一個 runner 通常只能同時吃有限 job，無法利用本機總控已具備的 4 claim workers + 4 executor slots；
3. GitHub workflow 被誤當成 Case queue / status / execution authority，導致 Case 進度與本機真實狀態脫節。

### 新架構

改成：

`ChatGPT -> GitHub workflow_dispatch -> 指定 runner -> openworkerctl <固定高階命令> -> localhost:8848 接受/查詢 -> workflow 立即退出`

workflow 只做 command transport，不做 business execution。

允許的高階命令固定為：

```text
supervisor_status
case_status
case_continue
queue_clear
```

對應本機命令：

```text
openworkerctl supervisor status
openworkerctl case status 0005
openworkerctl case continue 0005
openworkerctl queue clear DESKTOP-ODAQN0D
```

### 強制邊界

1. workflow 必須固定 machine label，並再次驗證 `COMPUTERNAME`。
2. workflow 不接受任意 shell、任意 script、任意 URL、任意 case id、任意 machine。
3. `case_continue` 只允許 Case `0005` + `DESKTOP-ODAQN0D`。
4. workflow 只允許呼叫已安裝的 `openworkerctl.exe` 或 repository 內經驗證的同一 binary build。
5. `case_continue` 成功標準只是本機總控接受投遞並回傳 receipt；workflow 不等待 Case 完成。
6. 真正排隊、claim、executor slot、retry、timeout、cancel、ledger 全在本機總控。
7. GitHub workflow run id 可以寫入 transport receipt 作 provenance，但不能作 Case execution truth。
8. `github_action_used_for_business_execution` 必須維持 `false`；另以 `github_action_used_for_command_transport=true` 明確區分 transport 與 execution。
9. artifact 不經 GitHub Actions，上傳 Google Drive 仍由 ODA 本機直接完成。
10. 後續 MCP 可與 GitHub transport 共用同一 command layer，不得分叉兩套業務邏輯。

### 目標 receipt

GitHub transport 層應輸出最小 JSON receipt，例如：

```json
{
  "schema": "openworker.command-transport.v1",
  "transport": "github_actions",
  "command": "case_continue",
  "case_id": "0005",
  "machine": "DESKTOP-ODAQN0D",
  "accepted": true,
  "github_action_used_for_command_transport": true,
  "github_action_used_for_business_execution": false
}
```

此 receipt 的用途只有證明「命令已送進本機 authority」，不能證明 Case 已完成。

### 並發效果

GitHub Actions 不再以 runner job 數量代表業務並發數。只要 command 被本機總控接收，真正並發由：

`durable queue -> 4 claim workers -> 4 executor slots`

決定。因此 GitHub dispatch workflow 應盡可能短命，避免因等待本機長任務而再次塞車。
