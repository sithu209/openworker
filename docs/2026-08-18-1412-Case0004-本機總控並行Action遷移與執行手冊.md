## 1. 新版最重要的差異

Case 0004 從現在起必須用新版架構理解，不能再把 GitHub Actions 當成本機工作的總控。

### 舊版

```text
ChatGPT
  -> GitHub workflow_dispatch
  -> GitHub Actions queue
  -> self-hosted runner
  -> 一個 Action 執行本機工作
  -> 等 Action 結束
  -> 從 GitHub 查結果
```

舊版問題：

- GitHub queue 變成不必要的中間層；
- 大模型常把 `queued` 誤當成本機忙碌；
- 同一台機器常被 runner / workflow concurrency 人為限制成近似串行；
- 查進度、清隊列、重試都繞 GitHub；
- 本機明明已有工具，仍要先 dispatch workflow 才能用；
- GitHub transport 狀態與真正 business state 容易混在一起。

### 新版

```text
ChatGPT Global Supervisor
  |-- 問 OpenWorker：現在做到哪、哪些 job/slot 在跑
  |-- 問 go-tool：這一步應使用什麼工具、參數、限制、負面知識
  |
  -> OpenWorker 本機總控
       |-- durable job / process
       |-- agent_slot A01
       |-- agent_slot A02
       |-- agent_slot A03
       |-- agent_slot A04
       |-- resource lock / retry / cancel / drain
       `-- workspace artifact + receipt
```

**核心改變不是「把 GitHub Action 換一個名字」，而是 scheduler / queue / progress / process ownership 全部回到本機 OpenWorker。**

## 2. OpenWorker 與 go-tool 的新版分工

### OpenWorker = 本機執行總控

OpenWorker 回答「工作現在怎樣」：

- fixed-machine routing；
- durable job；
- process lifecycle；
- queue；
- agent slots；
- dependency / fan-out / join；
- running / succeeded / failed / cancelled；
- retry / cancel / 一鍵清隊列；
- resource lock；
- workspace artifact / receipt；
- Case Worklist durable state。

因此**案例進度先問 OpenWorker，不再先查 GitHub workflow run。**

### go-tool = 本機工具總目錄／知識 authority

go-tool 回答「這一步怎麼做」：

- capability 是否存在；
- owning repo / executable / script；
- canonical local entrypoint；
- inputs / outputs；
- 是否可並行；
- resource lock；
- known failure / negative knowledge；
- 哪些舊 workflow 已是 legacy；
- 新版工具版本與使用方式。

因此**工具問題先問 go-tool，不由 Case 腳本自行猜工具。**

## 3. GitHub 在新版的定位

GitHub 仍然重要，但不再是 Case 0004 business execution bus。

保留用途：

- 原始碼與版本；
- 中文手冊／Case 文檔；
- commit / diff / review；
- CI / regression / smoke；
- 必要的外部 evidence；
- 本機 control plane 不可達時的 emergency transport。

不再作為 canonical：

- business scheduler；
- 本機 queue authority；
- progress authority；
- 長任務 process owner；
- 每一步都要 `workflow_dispatch` 的 transport。

所以「幾乎不經過 GitHub」的意思是：**REAL business execution 不需要經 GitHub；程式碼與手冊仍正常進 GitHub。**

## 4. Action 一詞在新版的意思

案例文檔若仍寫「Action」，要區分：

1. **Local Action / execution payload**：本機可以直接執行的能力、腳本、程式或既有 worktree payload；這是新版主線。
2. **GitHub Actions workflow**：GitHub scheduler 啟動的 workflow；新版只作 CI / fallback / emergency，不是 business 主線。

後續 Case 文檔優先使用 `local action`、`durable job`、`capability`，避免再把兩者混為一談。

## 6. queue / drain 的差異

新版清隊列是 OpenWorker 本機總控的即時管理功能。

```text
發現阻塞
-> OpenWorker 查 durable queue
-> 一鍵 drain / cancel stale jobs
-> durable clean receipt
-> 立即回 canonical Worklist
```

不再：

```text
發一個 GitHub Action
-> 等這個 Action 排到
-> 再由它清另一個 Action queue
```

queue-admin 是 operation capability，不是 Case business step；清隊列不能推進 Worklist business acceptance。
