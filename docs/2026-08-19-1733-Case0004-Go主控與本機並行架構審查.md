## 2. 正確控制鏈

Case 0004 正確流程應統一理解為：

```text
ChatGPT / LLM
  -> 先問 OpenWorker case_status
  -> OpenWorker Go Case Engine 判斷 current work / READY / dependency / gate
  -> case_continue
  -> OpenWorker 產生單步 durable work 或 fanout plan
```

## 3. Story viewport fanout 審查

目前 `go-runtime/internal/casecontroller/case0004_story_fanout.go` 已經實作 Case 0004 Story viewport 的 deterministic fanout。

其行為是：

1. 要求 step `kind = fanout`；

這部分方向正確，而且已經不是「尚未實作的 fanout 缺口」。

## 4. Continue / reconcile 審查

`go-runtime/internal/casecontroller/continue.go` 已具備以下正確行為：

- 若存在 active fanout，先 `reconcileFanout(...)`；
- fanout 未完成時返回 `fanout_active`，不重複建立 child work；
- current durable work 為 `pending / claimed / running` 時，只回傳 existing work，不 duplicate dispatch；
- completed 時驗證 acceptance evidence 後才把 step 標記 terminal-success；
- failed 時將真實 error 寫入 blocker 並 fail-closed；
- 多個 READY step 時走 registered fanout mapper；
- 單一 Story viewport fanout step 時走 `buildStoryViewportFanoutPlan(...)`；
- 一般單步則由 mapper 產生 inputs，建立 deterministic `work_id` 後 POST 到 go-tool durable queue。

這代表 Case 0004 已經具備 OpenWorker 作流程 authority、go-tool 作 queue/execution authority 的實際代碼基礎。

## 5. 需要修正的 Authority 表述

目前 `case-worklists/0004.json` 裡仍有幾個欄位容易讓大模型誤讀：

### 5.1 `parallel_policy.authority`

目前寫：

`go-tool-runtime-local-supervisor`

這會讓大模型誤以為 go-tool 是 Case 流程主控。

建議改成清楚拆分：

- `process_authority = openworker-go-case-engine/v1`
- `execution_authority = go-tool-runtime-local-supervisor`
- `queue_authority = go-tool-runtime:8848`

### 5.2 `fanout_queue_owner`

`fanout_queue_owner = go-tool-runtime:8848` 可以保留，但必須配套說明：

- **fanout decision owner / plan owner / join owner = OpenWorker**
- **fanout queue owner / child execution owner = go-tool**

不能把 queue owner 誤寫成 fanout process authority。

### 5.3 `openworker_role_for_fanout`

目前：

`single-coordinator-only`

方向沒有錯，但應更精確描述為：

`case-fanout-planner-reconciler-join-authority`

OpenWorker 不執行每個 child capability，但它負責決定 fanout、生成 plan、保存 fanout state、reconcile、join，以及決定 parent step terminal state。
