## 2. 一句话结论

Case0005 的正式架构是：

> **go-tool 告诉大模型“有哪些能力、工具怎么用”；OpenWorker 定义并解释密语，负责 Case 状态、依赖、调度和总控；go-tool-runtime 负责本机工具实际执行；GitHub Action 只作为短命令运输入口。**

因此必须严格区分：

```text
“告诉大模型怎么做”       → go-tool
“密语协议是谁定义/解析”   → OpenWorker
“Case 下一步该做什么”     → OpenWorker Case Engine / Local Supervisor
“工具实际怎么执行”        → go-tool-runtime
“把控制意图送到 ODA”      → GitHub transient transport + Runner Hook
```

**密语不是 go-tool 的业务逻辑。**  
**go-tool 也不是 Case0005 的总控。**  
**GitHub Action 更不是 Case0005 的业务执行器。**

## 3. 五个角色的正式职责

### 3.1 ChatGPT / LLM：决策者

大模型负责根据用户目标和当前状态决定：

- 要查询状态；
- 要清队列；
- 要让 Case 向前推进一批；
- 或者暂时只观察，不重复提交。

大模型不应该：

- 自己猜 Case dependency；
- 自己猜 READY step；
- 自己拼任意 PowerShell/CMD 给 ODA；
- 自己决定绕过审批 gate；
- 把 GitHub workflow 当成业务程序。

### 3.2 go-tool：给大模型看的能力说明书

go-tool 的定位是 **LLM capability registry / 操作说明书 / 工具入口**。

它应该告诉大模型：

- 当前有哪些 capability；
- capability 的用途；
- 参数格式；
- 哪些机器可用；
- 本机总控/队列/工具状态如何查询；
- 工具失败时应该用哪个 capability 诊断或修复。

简单说：

> **大模型不知道怎么操作时，先问 go-tool。**

但 go-tool 不拥有 Case0005 的业务流程 authority。它不能自行决定白雪公主下一步该做 Director、PPT、角色图还是视频。

### 3.3 OpenWorker：密语与 Case 总控 authority

OpenWorker 是 Case0005 的核心 authority，负责：

- Embedded Control schema；
- 密语 allowlist；
- request_id；
- machine 校验；
- 幂等；
- durable receipt；
- Case 状态；
- dependency；
- READY 判断；
- approval gate；
- fanout/join；
- reconcile；
- 本机 supervisor；
- 并行 work 编排。

所以：

> **密语的“语义”和“执行意图”属于 OpenWorker。**

### 3.4 go-tool-runtime：本机工具执行 authority

`go-tool-runtime :8848` 是实际工具/本机执行 authority。

它负责：

- durable queue；
- claim；
- executor；
- owning capability；
- 本机软件/脚本/工具调用；
- 真实结果返回；
- 工具层错误分类。

简单说：

> **OpenWorker 决定“做什么”，go-tool-runtime 负责“怎么实际做”。**

### 3.5 GitHub Action + Runner Hook：短命令运输层

GitHub 只负责让控制 envelope 进入指定的 ODA self-hosted runner。

它不应该包含：

- Case dependency；
- READY step 判断；
- business switch；
- fanout/join；
- artifact authority；
- 长时间 Case status transport；
- Case 业务结果搬运。

正式原则：

> **GitHub 是 transport，不是 supervisor。**

## 5. “密语”到底是什么

密语不是自然语言暗号，也不是 shell script。

它是一个受限的 OpenWorker control envelope。

固定 schema：

```text
openworker.control-envelope.v1
```

第一版 allowlist：

```text
CASE.STATUS
CASE.CONTINUE_BATCH
SUPERVISOR.STATUS
QUEUE.CLEAR
```

任何未知 command、错误 machine、非法 schema、非法 request_id、非法 max_parallel 都必须 fail-closed。

密语不允许携带：

- 任意 CMD；
- 任意 PowerShell；
- exe path；
- 任意脚本；
- 任意 business payload；
- 绕过 OpenWorker dependency 的 step 指令。

因此密语的本质是：

> **让大模型用很短、可验证、可重复、可审计的控制意图去驱动 OpenWorker 总控。**

## 7. 幂等与安全

### 7.1 request_id

每个有副作用命令必须有合法 request_id。

同一 request_id 重复进入 dispatcher 时：

1. 优先读取 `C:\ProgramData\OpenWorker\control-envelope\receipts\<request_id>.json`；
2. 若存在有效 receipt，直接返回原 exit_code 与原 result；
3. 不再次调用 `openworker.exe`；
4. 因此 `CASE.CONTINUE_BATCH` 不得因 GitHub 重试而重复制造 work。

### 7.2 Hook receipt

Hook 每次执行都写：

```text
C:\ProgramData\OpenWorker\hooks\receipts\<request_id>.json
```

至少包含：

```text
request_id
command
machine
accepted
exit_code
error_class
started_at
completed_at
dispatcher_result
```

### 7.3 Dispatcher receipt

Dispatcher 写：

```text
C:\ProgramData\OpenWorker\control-envelope\receipts\<request_id>.json
```

receipt 必须原子落盘，是 Control Envelope 幂等 authority。

## 13. 正确的 REAL 验收顺序

### Phase A：状态基线

1. `SUPERVISOR.STATUS`
2. 确认 go-tool `:8848` reachable
3. 确认 4 claim slots + 4 executor slots fresh
4. `CASE.STATUS 0005`
5. 记录当前 step、active work、leaf blocker、queue counts

### Phase B：必要时清队列

1. `QUEUE.CLEAR`
2. 再发一次 `QUEUE.CLEAR`
3. 两次都必须 success
4. 再查 `SUPERVISOR.STATUS`
5. queue pending/claimed/inflight 必须为 0
6. 4+4 slots 仍 fresh

如果本来没有阻塞，就不要为了测试而清正常 active work。

### Phase C：真实推进一次

只有 Phase A/B 证明没有不应存在的 active work 后：

1. 发唯一 request_id 的 `CASE.CONTINUE_BATCH`
2. OpenWorker reconcile
3. 只提交合法 READY work
4. 如果 Case 定义允许 fanout，则最多进入 4-slot local execution
5. 使用相同 request_id 再发一次
6. 第二次必须命中 durable receipt，不得重复制造 work

### Phase D：状态回读

推进后只读：

1. `CASE.STATUS`
2. `SUPERVISOR.STATUS`
3. current/active work
4. queue pending/claimed/inflight
5. claim slots 1–4
6. executor slots 1–4
7. heartbeat
8. last durable result

若 work 已 running，不再重复 continue。

### Phase E：业务成果验收

一旦某个业务 step 完成，必须检查：

1. artifact 是否真实存在；
2. 文件大小是否非 0；
3. 路径是否位于 Case0005 workspace/正式发布目标；
4. manifest/hash 是否存在；
5. Case status 是否引用该 artifact；
6. 若要求 Drive 发布，Drive revision 是否真实存在；
7. ChatGPT 是否能实际读取并审查成果；
8. 审批 gate 是否根据真实审查结果推进。

只有 Phase E 通过，才允许说“有成果”。
