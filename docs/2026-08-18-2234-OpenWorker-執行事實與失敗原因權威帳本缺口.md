# OpenWorker 執行事實與失敗原因權威帳本缺口

時間：2026-08-18 22:34 +08:00

## 問題

OpenWorker 過去雖然能保存 job status、stdout/stderr 路徑與事件，但對大模型/操作員仍不夠直接。當 Case 0005 白雪公主 bootstrap 沒有在 ODA 建立 `D:\AI-Work\jobs\0005-SNOW-WHITE` 時，外部只能看到「沒有目錄」，卻無法直接從 OpenWorker 得知：

- 本次要求做什麼；
- 實際執行到哪個 stage；
- 哪些 preflight 已通過；
- 有沒有真的進入 mkdir；
- 是否成功；
- 失敗的原始錯誤；
- 為什麼失敗；
- 下一步應該修什麼。

這會迫使 ChatGPT 反查 GitHub Action、程式碼或猜測原因，違反「OpenWorker 為執行事實權威」的架構。

## 權威邊界

- go-tool：回答「這一步應該怎麼做、用什麼工具、有哪些正負面知識」。
- OpenWorker：回答「實際做了什麼、在哪台機器做、做到哪、成功沒、為什麼失敗、證據在哪」。
- GitHub Actions：只做安裝、升級、修復與 bootstrap ingress；不得作為 Case business execution 的權威。
- Google Drive：只傳成果供語意/視覺審查，不作命令 ingress。

## 本批實作

### 1. Case bootstrap 結構化 failure diagnostic

`POST /v1/cases/bootstrap` 的 preflight/route/materialize/queue submit 失敗現在要回傳：

- `ok=false`
- `case_id`
- `machine`
- `stage`
- `attempted_action`
- `reason`
- `next_action`
- `checks`
- `observed_at`

同一份 diagnostic 會寫入 durable cluster control ledger：

- event type：`case_bootstrap_failed`

成功時回傳：

- `ok=true`
- `workspace_created=true`
- `workspace_marker`
- `stage=accepted`
- `attempted_action`
- durable job ACK
- 完整 checks

因此 Case 0005 若仍無法落檔，OpenWorker 應能明確區分：

- request decode 失敗；
- required field 缺失；
- controller/python 不合法；
- cluster route 失敗；
- workspace path 解析失敗；
- OpenWorker checkout 不存在；
- case manifest/worklist 不存在；
- case spec 不存在；
- `os.MkdirAll` 失敗；
- durable queue submit 失敗。

### 2. 一般 Job durable execution summary

每個實際 Job attempt 在開始時新增 `attempt` event，保存：

- machine
- cwd
- workspace
- command

每個 Job terminal finish 時新增 `execution_summary` event，schema：

`openworker.execution-summary/v1`

至少包含：

- `job_id`
- `dispatch_id`
- `machine`
- `status`
- `succeeded`
- `attempted_action`
- `cwd`
- `workspace_root`
- `exit_code`
- `reason`
- `stdout_path`
- `stderr_path`
- `stdout_tail`
- `stderr_tail`
- `started_at`
- `finished_at`
- `next_action`
- `recorded_at`

這份 receipt 必須是 durable event，不可只存在 console log。

## 失敗分類原則

第一階段採 deterministic-first：

- `machine mismatch` → 修正 COMPUTERNAME 路由；
- `worktree` → 修 repository/worktree；
- `process start failed` → 修 executable/path/env；
- timeout → 檢查工具 log 與 timeout 設定；
- cancelled → 確認是否為操作員意圖；
- 其他 → 以 stderr tail + tool receipt 為第一證據，不由 LLM 猜原因。

未來可再把分類擴展成穩定的 FailureReceipt schema，但不得把 deterministic 原始錯誤覆蓋掉。

## 驗收測試

新增 runtime test：建立一個刻意 exit 7 並向 stderr 寫入 `boom-detail` 的 job，要求 terminal event 必須存在 `execution_summary`，而且至少同時包含：

- `succeeded=false`
- `boom-detail`
- `next_action`

沒有 execution summary 即視為 OpenWorker 執行帳本不完整。

## Case 0005 的直接驗收

升級 ODA OpenWorker 後，再送 Case 0005 bootstrap。必須出現以下兩種結果之一，禁止模糊狀態：

### PASS

- `D:\AI-Work\jobs\0005-SNOW-WHITE\.openworker` 實際存在；
- API 回 `workspace_created=true`；
- durable bootstrap job ACK `accepted=true`；
- 後續由 ODA local supervisor 執行 Case business steps。

### FAIL

OpenWorker 必須回傳精確 `stage / attempted_action / reason / checks / next_action`，並在 durable control ledger 留下同一份失敗診斷。

不得再只回答「沒有建立」「failed」或依賴 GitHub Action log 才知道原因。
